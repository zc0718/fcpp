## 1. 结论速览

1. **两个已知问题全部实锤**，且比描述的更严重：
   - commit 无强制门禁 ✅确认（无 commitlint / 无 PR title 检查 / 无 branch protection 配置）。
   - clang-tidy/clang-format 检出错误被跳过 ✅确认（`security-linters.yml:66,84` 两处 `continue-on-error: true`，job 永不失败）。
2. **额外发现 P0 级设计缺陷**：`_shared/gitmoji.md` 推荐的 canonical form `type(:emoji:): description` **与 semantic-release 默认解析器不兼容**（见上表实测）→ 即使 release 流水线被触发，`commit-analyzer` 也读不到任何版本变更 → **版本号永不自增、CHANGELOG 为空**。
3. **release 链路当前是不可达死代码**：`metadata.json` 中 `build_type=Debug` + `workflow_triggers.release=false`，而 release 触发条件要求 `Release` + emoji + 开关，从未被真实验证过。
4. **`package.json` 缺失**：semantic-release 依赖根目录 `package.json` 作为发布上下文，`semver-release.yml` 的 `npx semantic-release` 在真实触发时会失败。
5. **配置文件位置阻止插件化**：`.clang-format`/`.clang-tidy` 只存在于 `.github/misc/`，不在编辑器/工具链的自动发现链上——本地（含未来 VS Code 插件）与 CI 行为不一致。
6. 固化公司标准所需的治理层（CODEOWNERS / CONTRIBUTING / 模板 / JSON Schema / dependabot）整体缺失（见 §5 P1 清单）。

## 4. 用户两个已知问题的确认与修复方案

### 4.1 问题 1：commit 门禁缺失 → 固化为 push/PR 门禁

**现状证据**：仓库无 `.commitlintrc`/`commitlint.config.js`、无 husky/pre-commit、无 PR title 检查、无 branch protection 文档；`ci-orchestrator.yml` 对 commit 内容零校验。

**修复（按依赖顺序）**：

1. **先修解析器兼容**（否则门禁过了、版本不动）：
   - `.releaserc.json` 给 `@semantic-release/commit-analyzer` 增加 `parserOpts.headerPattern`（scope 允许 `:emoji:`）：
     ```json
     ["@semantic-release/commit-analyzer", {
       "preset": "conventionalcommits",
       "parserOpts": {
         "headerPattern": "^(\\w*)(?:\\(([^)]*)\\))?!?: (.*)$",
         "headerCorrespondence": ["type", "scope", "subject"]
       }
     }]
     ```
   - 或退而求其次：canonical 改为 `feat!: desc` + emoji 移到正文/trailer，避免自定义 parser。
2. **新增 commit-lint job**（挂到 `ci-orchestrator.yml`，push + pull_request 均执行）：
   - 用 `wagoid/commitlint-github-action` + `commitlint.config.js`（自定义 parserPreset 与 canonical regex 对齐：`^(feat|fix|perf|docs|test|build|ci|refactor|style|chore)(\\(:\\w+:\\))?!?: .+`）。
   - PR 场景加 `amannn/action-semantic-pull-request` 校验 PR title（squash-merge 场景兜底）。
3. **真正的门禁靠 branch protection ruleset**：把 commit-lint + build + tests 设为 main 分支 required status checks。仅靠 push 上的 job 只能"事后报告"，推上 main 的坏提交无法拦截——这是公司标准化的关键动作（建议把 ruleset 要求写进 `CONTRIBUTING.md`）。
4. **边界修复**：`github.event.commits.*.message` 仅含最近 20 条 commit，gitmoji 触发在长 push 中会漏判 → 改用 `github.event.head_commit.message` + 全量 `git log` 兜底。

### 4.2 问题 2：clang-tidy/clang-format 门禁太松

**现状证据**：`security-linters.yml:66,84` 两个 MegaLinter step 均 `continue-on-error: true` → 任何 lint 失败都不会红 job；`.mega-linter.yml` 未设 `FAIL_IF_UPDATED_SOURCES`，且 `APPLY_FIXES_MODE: commit` 自动提交修复，形成"修不好就静默"的观感。

**修复**：
1. 删除两处 `continue-on-error: true`，改为 job 级失败；将 `APPLY_FIXES` 改为 `none`（严格模式）或保留修复但要求二次提交后重跑。
2. MegaLinter 前增加**轻量原生 gate**（快速失败 + 友好 diff 输出）：
   ```bash
   clang-format --dry-run --Werror --style=file:.github/misc/.clang-format include/ src/
   clang-tidy --config-file=.github/misc/.clang-tidy src/*.cpp -- -std=c++17
   ```
3. 产出 SARIF 已有 `SARIF_REPORTER: true` ✅，可作为门禁状态检查的 artifact（对接未来插件一键查看）。
